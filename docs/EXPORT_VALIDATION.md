# Deterministic WebM/MP4 export and validation

## Export contract

The saved active sequence is authoritative. `durationFrames` is the exact requested output video-packet count; the rational sequence frame rate (`numerator / denominator`) determines frame boundaries; sequence dimensions are used unless an export-size preset is selected. The end-exclusive endpoint is converted using the existing frame-count rule. Project/source media remain local and are never copied into project JSON or uploaded.

`src/lib/timelineExport.ts` is the shared production path called by the editor and packaged fixtures. It validates the saved project snapshot, resolves local source blobs, decodes timestamp-addressed source frames through Mediabunny `CanvasSink`, maps visible clips/tracks into the saved project canvas, composes the explicit `fit`/`fill`/`stretch` mode and background, mixes embedded/separate audio in bounded chunks, and sends frames/sound to the selected Mediabunny output. WebM remains VP9/Opus; MP4 is genuine H.264/AVC plus AAC-LC when readable timeline audio is present. MP4 capability checks use the exact dimensions, frame rate, bitrate, audio sample rate and encoder preferences intended for export. Unsupported MP4 configurations fail clearly without fallback. Frame indices and rational timestamps—not `requestAnimationFrame`, media-element seek events, or playback callbacks—drive both formats. Encoder/muxer work is awaited and the output is finalized before inspection.

A success requires exact equality across requested, rendered, submitted, encoded, and finalized video-packet counts; the encoded track dimensions must exactly match the selected output canvas; and the file must report the selected container/codecs (MP4 requires AVC plus AAC-LC when audio is expected). It also requires monotonic video packet timestamps within policy, successful decode/content checks for three lightweight output probes (first, middle, last), required audio presence and decoded audio buffers whenever readable source audio was selected, finite video/audio/container durations within format-specific packet/timebase bounds, and the effective encoder configurations. Only then may the editor download the file. On failure it offers a local JSON diagnostic with stage, counts, measurements when available, encoder configuration, duration deltas/bounds, error, and no source media.

## Numerical acceptance policy

Timebase is measured from the finalized track; the current Mediabunny Matroska muxer uses a 1 ms tick. Opus output uses 20 ms packets in the supported path. At 30 fps, 48 kHz audio, and a 1 ms timebase, the enforced bounds are:

| Measurement | Bound | At 30 fps / 48 kHz |
| --- | --- | ---: |
| Video packet PTS versus frame index | `half frame period + half actual video timebase tick` | 17.166667 ms |
| Audio signal onset / A/V event alignment | `half Opus packet + half actual audio timebase tick + one audio sample` | 10.520833 ms |
| Audio duration | `one Opus packet + half actual audio timebase tick + one audio sample` | 20.520833 ms |
| Container duration | larger of the applicable video and audio duration bounds | 20.520833 ms with expected audio |
| Lightweight decoded content probes | RGB mean absolute error no greater than 48/255 on a 16×9 downsample; timestamp remains within video PTS bound | 48/255 |

For MP4/AAC-LC, the audio packet term is derived from a 1024-sample access unit (`1024 / measured sample rate`), not the WebM Opus 20 ms packet. For example, at 48 kHz and a 1 ms audio timebase, AAC onset/A/V tolerance is about 11.188 ms and AAC audio-duration tolerance is about 22.354 ms. This is a codec-packetization-specific bound; it does not change the existing WebM/Opus limits. The tolerances scale with frame period, the output track's reported timebase, packet duration, and audio sample rate; they are not a blanket one-frame allowance. Missing audio is a failure when readable source audio was expected. The light local probe gate is not a full pixel-by-pixel certification; CI independently decodes every synthetic output frame and all synthetic audio samples.

## Root-cause context and historical measurement

The earlier `MediaRecorder`/canvas-capture implementation depended on display callbacks, browser capture cadence, and real-time playback; it could not set every frame PTS, await exact backpressure, or guarantee packet identity. The old Windows playback report's callback/decode counts were playback measurements, not actual output-file packet counts.

The historical case remains **unverified**. 667 frames at 30 fps means 22.233333 s; a reported 22.646 s is 0.412667 s longer. An entered 22.21 s endpoint also rounds to 667 frames under the timeline endpoint rule. The original project, source media, WebM, device and measurement logs are unavailable. Audio/container tail, legacy capture cadence, and measurement-source differences remain hypotheses only. A unit test demonstrates that the new numerical duration policy rejects a 0.412667 s tail; that arithmetic does not reproduce or resolve the historical export.

## Local diagnostic tool

`/export-validation.html` is a local-only page in the static production bundle. Save the active project, select its JSON and the WebM, and run the check. The project JSON is reread immediately before each run. The tool counts encoded packets, attempts a full video decode, requires decoded frame count to match the saved sequence count, and measures video/audio/container duration using the policy above. Playback drops, callback cadence, decoded playback frames and waiting events remain a separate device/browser playback section. The manual page does not certify A/V synchronization or inspect every decoded pixel. Neither file is uploaded.

## Packaged Windows CI fixture and independent validator

The Windows workflow builds/packages Electron, generates two short local VP9/Opus source videos with known frame IDs and aligned audio pulses, serializes the schema-v2 fixture project to JSON, reparses that saved snapshot, and invokes the same `exportTimelineProject` function used by the editor. The project contains trimmed ranges, adjacent split clips, cuts, a five-frame intentional gap, and a five-frame offline clip. The expected frame schedule uses a literal placement table and computes the requested source time independently of production clip-selection/time-mapping helpers; expected source identity is the last independently decoded source PTS at or before that time, matching the documented sampling contract without assuming a 30 fps frame's rounded WebM PTS is exactly `index / 30`. The smoke decodes all timeline-output frames in Mediabunny, checks source/frame identity, black intervals, every visible flash position, exact PTS/counts, audio packet/duration/pulse onsets and per-event A/V offsets. Pulse-to-flash A/V checks pair onset events at their designated output frames, while the per-frame identity oracle separately permits a flash image to persist if source PTS rounding holds that decoded frame for an adjacent output sample. The production service itself performs its normal finalized-file gates.

The workflow saves the generated source files, exact saved-project JSON, fixture manifest, actual production WebM and required MP4/custom-dimension outputs, smoke report, and independent validation report as CI artifacts on both success and failure (when produced). A CI-only FFmpeg/ffprobe script separately counts packet/frame metadata, fully decodes all video and audio, verifies every output identity pixel pattern and timestamp, checks audio packet timestamps, detects the seven pulse onsets, compares all A/V flash offsets, and measures video/audio/container durations with the output timebases. FFmpeg/ffprobe is not a runtime or installer dependency. The report records the effective WebCodecs encoder configurations. A `hardwareAcceleration` configuration field is a preference, not evidence that a physical hardware encoder was used; physical encoder use remains unverified.

## Desktop chunked-save implementation — 2026-10-29

Desktop exports now use Mediabunny `StreamTarget` writes over acknowledged IPC chunks (each at most 8 MiB) into a per-export `.part` file. Once muxing completes, the main process syncs the temporary file and exposes bounded ranged reads; the renderer re-runs the same packet, timestamp, track, decoded-sample, frame-count, duration, and encoder-configuration checks through Mediabunny `CustomSource` before the main process atomically publishes the file without overwriting an existing name. Failed/cancelled runs abort and remove the partial file. The begin call checks estimated free space; streaming output has a 64 GiB ceiling. Desktop MP4 uses standard non-fast-start layout so muxing does not buffer all media for an in-memory metadata rewrite. The browser-download path remains buffered.

Local regression tests cover streamed begin/write/prepare/ranged-read/commit/abort behavior, out-of-order writes, gap rejection, collision protection and chunk bounds. The packaged synthetic smoke harness now exercises the streamed target and asserts that the muxer result retains no full output buffer. `npm run build` type-checks and bundles this path, but this Linux turn has not run the packaged Windows smoke, the MP4/WebM independent validators, 30-minute exports, or target-device memory sampling. Existing validation tolerances and checks were not changed; successful end-to-end streaming export is not claimed until Windows CI passes.

## Target-device procedure and release gates

1. Record the device model, Windows build, exact Electron/Chromium versions, display/GPU, power profile, and effective encoder configurations (mark hardware use unknown unless independently confirmed).
2. Save a repeatable project containing relinked sources, cuts, trimmed clips, a gap, and audio. Preserve the original project/media and export at the exact sequence FPS/resolution; include a long timeline and target resolutions where practical.
3. Use the local validation page and an independent FFmpeg/ffprobe installation to compare the actual exported file. Record tool versions, counts, per-track/container durations, PTS, decoded frame/audio results, and errors. Keep playback drop/callback metrics separate.
4. Gate exact requested/rendered/submitted/encoded/output packet counts; every video PTS within half a frame plus half an actual timebase tick; audio presence when expected; audio/container durations within the packet/timebase/sample bounds above; full decode; no A/V drift beyond half an Opus packet plus timebase/sample; correct visual content; and repeatable success/cancellation/failure cleanup.
5. Do not average away failed exports. Preserve success and failure diagnostics and actual output artifacts when privacy-safe. A synthetic CI success is not a user-media or target-device pass.
