# Known limitations — foundation build 0.1.0

ClipWright is a browser-based editing foundation, not a complete desktop video editor.

- **Packaging and storage:** The unsigned x64 NSIS installer was built by GitHub Actions, passed its packaged-renderer/preload smoke test, and the installed build was confirmed working. It is still an unsigned preview, not a supported public release, and there is no portable build. The Windows desktop app provides native `.cwproject` open/save, 650 ms debounced autosave for linked files, atomic replacement, and up to ten recovery checkpoints per project; project-list entries/documents and preferences also remain in browser-profile localStorage. Browser builds continue to use local storage and explicit download snapshots. Source media is never bundled, and browser-picked media must be relinked after restart.
- **Media references:** Local video and audio files are inspected in-browser and held in memory through revocable object URLs for the current page session. Project documents retain filename-only `browser-session` references and metadata, never media bytes or temporary URLs. Relinking is required after reload. Browser imports do not persist usable filesystem paths. In the desktop library, linked absolute media must have a SHA-256 fingerprint before it is made available; an absolute asset without one reports unavailable and must be relinked. This affects existing schema-v1 assets (including v1 documents migrated in memory) and schema-v2 assets only when `pathKind` is `absolute` and `fingerprint` is absent; project-relative managed assets and browser-session assets are unaffected. Fingerprinted linked media is verified when first resolved in a session and successful checks are cached only in main-process memory by absolute path, size, and modification time; changes to either metadata value trigger a full re-hash. As with any metadata-keyed cache, content replaced while preserving both size and modification time is not detected until the cache is cleared by restarting the app or those metadata values change. Import/relink preflight rejects empty files and obvious media-kind/MIME mismatches, probes metadata before replacing a session source, and prevents overlapping reads; decoder/codec compatibility still depends on the browser. Image picker ingestion is not supported.
- **Codec and frame accuracy:** Preview uses native browser `<video>` decoding. Container/codec support, seek latency, and actual presented frames depend on the browser and operating system. Timeline times and edits are quantized to the project frame rate, but preview seeking is still controlled by browser media elements and is not a decoder-level frame-accurate guarantee. Export separately uses timestamped Mediabunny frame readers. The current packaged Windows production and independent FFmpeg/ffprobe checks passed in [run 40906510630](https://github.com/yetiwrld/ClipWright/actions/runs/40906510630), including H.264/AAC-LC MP4, video-only MP4, exact portrait/custom dimensions and frame identities. Real user-media output and other target-device behavior remain unverified. WebCodecs does not expose physical hardware versus software backend. Browser-reported source duration is not independently verified against container metadata.
- **Playback scope:** The timeline is the master clock and advances with `requestAnimationFrame`; video elements follow it, two decks preload the next active source, source-time drift is corrected, gaps render black, and playback stops at the last clip on any track. Audio clips on separate tracks play and mix against that clock, follow seeks/trims, and honor track mute, per-track gain/pan, saved audio-track solo, plus the shared preview-volume control. Track hide/show and audio solo persist in the project and affect export. Preview is a single active video clip, not a composited multi-layer output. On-demand stereo waveform previews are session-only, not saved in project documents, and limited to relinked files up to 20 MB and 3 minutes. Decoding currently runs in the renderer and may briefly affect responsiveness. Audio automation and audio effects are not included.
- **Editing and export scope:** Clip move, same-type track changes, trim, split, normal/ripple delete, multi-selection, marquee selection, snapping, copy/paste/duplicate at the playhead, and session-only undo/redo are implemented. Track mute/lock, audio gain/pan, and hide/show/solo render state are project-persisted; undo history is not serialized and resets when the page closes. Export retains deterministic WebM VP9/Opus and adds MP4 H.264/AVC plus AAC-LC. MP4 is offered only after runtime checks against the selected dimensions, frame rate, bitrate, audio sample rate and expected tracks; unsupported MP4 is unavailable and never silently falls back. The export selector writes correct `.webm`/`.mp4` extensions. Project settings now support landscape, portrait, square, 4:3, 3:4, 4:5, 5:4, 21:9 and custom whole-pixel dimensions, saved fit/fill/stretch composition and background color. The selected canvas is used by preview and both encoders; final-file inspection requires exact dimensions, with no implicit source-size override or H.264 odd-dimension rounding. Before success, both formats require exact frame counts, monotonic video PTS, three decoded content probes, expected audio-track presence, per-track/container duration bounds and effective encoder configuration; failure saves a local diagnostic without media. At 30 fps/48 kHz/1 ms, existing WebM bounds remain 17.167 ms video PTS, 10.521 ms audio onset/A/V, and 20.521 ms audio/container duration. AAC limits use actual 1024-sample packetization. Resolution presets remain sequence plus 720p/540p/360p and compact/standard/high bitrates. In the Electron desktop app, encoded output is sent in acknowledged chunks of at most 8 MiB to a same-folder temporary file, re-read by bounded ranges for the unchanged post-export checks, and atomically published only after validation; startup checks estimated free disk space and streamed saves are capped at 64 GiB. Desktop MP4 uses regular non-fast-start layout to avoid an in-memory metadata rewrite. Browser downloads still use an in-memory buffer, and desktop source media are still materialized as renderer Blobs before export; long-run target-device memory/performance remains unmeasured. This is not offline desktop rendering or a full multi-layer compositor. The prior WebM-only saved-project/FFmpeg validation passed on a Windows CI runner; the current required MP4/WebM production tests passed in [run 40906510630](https://github.com/yetiwrld/ClipWright/actions/runs/40906510630), using synthetic media only. Imported user media, broad device coverage, and long-run memory behavior are not certified. Offline sources produce black/silent segments. No effects, captions, AI analysis, transcription, or reframing are included.
- **Layout:** The editor stays below the project top bar. Navigation and media panels collapse; the preview/timeline divider is resizable. Track headers and ruler remain fixed while the timeline canvas scrolls, with responsive zoom and auto-follow. Timeline height and zoom preferences are browser-local, not project settings.
- **Dependencies and assets:** No FFmpeg binary/library, AI model, cloud provider, database, plugin system, telemetry, or credential store is included. The project-card background is decorative, not a real thumbnail. The supplied icon's redistribution rights have not been independently verified.
- **Verification (current branch):** Local `npm test` (112 tests across 15 files), `npm run test:desktop` (41 tests), `npm run build`, and `git diff --check` pass for the current worktree. The Windows packaged MP4/WebM production smoke and independent FFmpeg/ffprobe checks passed historically in [run 40906510630](https://github.com/yetiwrld/ClipWright/actions/runs/40906510630), before the current streamed-save changes; that run does not verify the new IPC streaming path. Genuine H.264 High/AAC-LC MP4 and VP9 WebM files were independently decoded and inspected; all required video-only, A/V, portrait, custom-dimension, composition, unsupported-configuration and cancellation/retry checks passed. The available Linux agent has no Xvfb, `DISPLAY`, FFmpeg or ffprobe and cannot run the packaged-media test locally. Earlier Windows run [40879301564](https://github.com/yetiwrld/ClipWright/actions/runs/40879301564) is a prior WebM-only result: VP9/Opus, 65/65 decoded frames, 109 Opus packets, zero identity mismatches, and measured video/audio/container durations of 2.166/2.1735/2.180 s against 2.166667 s expected. It is not MP4 or current-branch evidence; CI artifact upload passed, but agent-side download returned EOF. Physical hardware encoding is not established by WebCodecs configuration. Earlier pre-change sandbox diagnostics remain historical only: 1080p exports produced 20–28 frames over 4 seconds versus 120 expected; subsequent 720p/540p/360p runs produced 54/72/98–109 packets and were inadequate. The former 22.646 s report remains unexplained: 667 frames at 30 fps is 22.233333 s, a 0.412667 s difference; the original file/log/device context is unavailable, and a 22.21 s expectation still rounds up to 667 frames. Keep playback callback/drop metrics distinct from encoded-file measurements. Long-duration 30000/1001 output, user-media A/V sync, memory pressure, packaged cancellation/failure recovery, broad Windows codec/device coverage, and actual hardware/software encoder backend remain unverified until independently measured on target devices.

## Security validation update — 2026-10-29

Desktop project envelopes and renderer project documents now require asset IDs to use the safe stable-ID character set and validate any stored fingerprint as a lowercase 64-character SHA-256 digest. Backup creation computes the digest from the resolved source, refuses a mismatch, confines copied media to its temporary backup directory, and restore validates the manifest before copying. Existing valid v1/v2 documents without a fingerprint remain loadable; invalid non-hex fingerprints now require relinking or correcting the manifest rather than being trusted.

Portable filename handling — 2026-10-29: project-save suggestions, managed/backup media names, and MP4/WebM export names now prefix Windows device basenames (including COM/LPT superscript forms) with `_`, regardless of host OS. Similar ordinary names such as `console` and `COM10` remain unchanged.

Local media protocol — 2026-10-29: Electron 45 `protocol.handle` requests expose `initiatorOrigin` but no originating `webContentsId`. Media requests now require the exact trusted renderer origin, and CORS returns only that origin. UUID media URLs remain capability tokens tracked by their owning WebContents and are revoked on top-level navigation; this is not a per-window request binding.
