# Known limitations — foundation build 0.1.0

ClipWright is a browser-based editing foundation, not a complete desktop video editor.

- **Packaging and storage:** The unsigned x64 NSIS installer was built by GitHub Actions, passed its packaged-renderer/preload smoke test, and the installed build was confirmed working. It is still an unsigned preview, not a supported public release, and there is no portable build. The Windows desktop app provides native `.cwproject` open/save, 650 ms debounced autosave for linked files, atomic replacement, and up to ten recovery checkpoints per project; project-list entries/documents and preferences also remain in browser-profile localStorage. Browser builds continue to use local storage and explicit download snapshots. Source media is never bundled, and browser-picked media must be relinked after restart.
- **Media references:** Local video and audio files are inspected in-browser and held in memory through revocable object URLs for the current page session. Project documents retain filename-only `browser-session` references and metadata, never media bytes or temporary URLs. Relinking is required after reload. Imported path references are not automatically verified or resolved. Import/relink preflight rejects empty files and obvious media-kind/MIME mismatches, probes metadata before replacing a session source, and prevents overlapping reads; decoder/codec compatibility still depends on the browser. Image picker ingestion is not supported.
- **Codec and frame accuracy:** Preview uses native browser `<video>` decoding. Container/codec support, seek latency, and actual presented frames depend on the browser and operating system. Timeline times and edits are quantized to the project frame rate, but preview seeking is still controlled by browser media elements and is not a decoder-level frame-accurate guarantee. Export separately uses timestamped Mediabunny frame readers, but Windows packaged execution and real user-media output remain unverified for the current changes. Browser-reported duration is not independently verified against container metadata.
- **Playback scope:** The timeline is the master clock and advances with `requestAnimationFrame`; video elements follow it, two decks preload the next active source, source-time drift is corrected, gaps render black, and playback stops at the last clip on any track. Audio clips on separate tracks play and mix against that clock, follow seeks/trims, and honor track mute, per-track gain/pan, saved audio-track solo, plus the shared preview-volume control. Track hide/show and audio solo persist in the project and affect export. Preview is a single active video clip, not a composited multi-layer output. On-demand stereo waveform previews are session-only, not saved in project documents, and limited to relinked files up to 20 MB and 3 minutes. Decoding currently runs in the renderer and may briefly affect responsiveness. Audio automation and audio effects are not included.
- **Editing and export scope:** Clip move, same-type track changes, trim, split, normal/ripple delete, multi-selection, marquee selection, snapping, copy/paste/duplicate at the playhead, and session-only undo/redo are implemented. Track mute/lock, audio gain/pan, and hide/show/solo render state are project-persisted; undo history is not serialized into project files and resets when the page closes. WebM export submits an exact frame-index plan to WebCodecs/Mediabunny, reads mapped source frames by timestamp through Mediabunny `CanvasSink` instead of HTML video seek events, waits for encoder/muxer backpressure, finalizes, and checks actual output packets and separate video/audio/container durations before download. It offers sequence resolution by default plus 720p/540p/360p long-edge presets and compact/standard/high bitrate profiles. It requires supported browser WebCodecs codecs and can consume substantial memory because the output is held in a buffer. It is deterministic frame-index rendering, but not offline desktop rendering or a full compositor; Windows target behavior remains unverified. Offline sources produce black/silent segments. No effects, captions, AI analysis, transcription, or reframing are included.
- **Layout:** The editor stays below the project top bar. Navigation and media panels collapse; the preview/timeline divider is resizable. Track headers and ruler remain fixed while the timeline canvas scrolls, with responsive zoom and auto-follow. Timeline height and zoom preferences are browser-local, not project settings.
- **Dependencies and assets:** No FFmpeg binary/library, AI model, cloud provider, database, plugin system, telemetry, or credential store is included. The project-card background is decorative, not a real thumbnail. The supplied icon's redistribution rights have not been independently verified.
- **Verification:** The current audit refresh passes 76 unit tests across 11 files, the production build, 9 desktop tests, `node --check electron/main.cjs`, and `git diff --check`. Unit coverage includes project validation/migration, frame-time/rational-rate arithmetic, timeline source-time selection, and schema-compatible saved track render state. This Linux environment has no Xvfb, Chromium, FFmpeg, or `DISPLAY`; the packaged Windows identity smoke has not run, and the synthetic fixture is not evidence about user media, long exports, A/V offset, codec/device behavior, or target hardware. Earlier pre-change sandbox diagnostics remain historical only: 1080p exports produced 20–28 frames over 4 seconds versus 120 expected; subsequent 720p/540p/360p runs produced 54/72/98–109 packets respectively and were inadequate. The former 22.646 s report also remains unexplained: 667 frames at 30 fps is 22.233333 s, a 0.412667 s difference; the original file/log/device context is unavailable, and a 22.21 s expectation would still round up to 667 frames. Keep playback callback/drop metrics distinct from encoded-file measurements. Long-duration 30000/1001 output, A/V offset, embedded-audio trim/split behavior, output-buffer memory pressure, codec coverage, cancellation/failure recovery on packaged builds, and broad Windows hardware compatibility still need dedicated verification.
