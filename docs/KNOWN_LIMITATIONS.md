# Known limitations — foundation build 0.1.0

ClipWright is a browser-based editing foundation, not a complete desktop video editor.

- **Packaging and storage:** An Electron main/preload shell and unsigned x64 NSIS installer configuration exist, and a Windows CI workflow is set up to build and smoke-test it. The workflow has not yet run, so there is no verified installer artifact or supported Windows release; there is no portable build. Project-list entries, schema-v2 project documents, theme settings, and timeline layout preferences still use browser localStorage. `.cwproject` import/download is supported, but saving is a manual snapshot—not a managed project-folder save or atomic file write. Browser storage can be cleared; keep independent copies of important work.
- **Media references:** Local video and audio files are inspected in-browser and held in memory through revocable object URLs for the current page session. Project documents retain filename-only `browser-session` references and metadata, never media bytes or temporary URLs. Relinking is required after reload. Imported path references are not automatically verified or resolved. Import/relink preflight rejects empty files and obvious media-kind/MIME mismatches, probes metadata before replacing a session source, and prevents overlapping reads; decoder/codec compatibility still depends on the browser. Image picker ingestion is not supported.
- **Codec and frame accuracy:** Preview uses native browser `<video>` decoding. Container/codec support, seek latency, and actual presented frames depend on the browser and operating system. Timeline times and edits are quantized to the project frame rate, but preview seeking is still controlled by browser media elements and is not a decoder-level frame-accurate guarantee. Browser-reported duration is not independently verified against container metadata.
- **Playback scope:** The timeline is the master clock and advances with `requestAnimationFrame`; video elements follow it, two decks preload the next active source, source-time drift is corrected, gaps render black, and playback stops at the last clip on any track. Audio clips on separate tracks play and mix against that clock, follow seeks/trims, and honor track mute, per-track gain/pan, session-only audio-track solo, plus the shared preview-volume control. Preview is a single active video clip, not a composited multi-layer output. On-demand stereo waveform previews are session-only, not saved in project documents, and limited to relinked files up to 20 MB and 3 minutes. Decoding currently runs in the renderer and may briefly affect responsiveness. Audio automation and audio effects are not included.
- **Editing and export scope:** Clip move, same-type track changes, trim, split, normal/ripple delete, multi-selection, marquee selection, snapping, copy/paste/duplicate at the playhead, and session-only undo/redo are implemented. Track mute/lock and audio gain/pan state are project-persisted and undoable; hide/show is session-only. Undo history is not serialized into project files and resets when the page closes. Experimental browser WebM export records the timeline in real time through canvas capture, Web Audio, and `MediaRecorder`; it offers sequence resolution by default plus 720p/540p/360p long-edge presets and compact/standard/high target bitrate profiles, but requires supported browser codecs and can consume substantial memory. The app exposes target bitrate profiles, not a guaranteed visual-quality level, and warns when measured canvas updates are below 90% of the expected frame count; this does not measure encoder-dropped frames. Offline sources produce black/silent segments. It is not deterministic/offline rendering, a full compositor, or a production export pipeline. No effects, captions, AI analysis, transcription, or reframing are included.
- **Layout:** The editor stays below the project top bar. Navigation and media panels collapse; the preview/timeline divider is resizable. Track headers and ruler remain fixed while the timeline canvas scrolls, with responsive zoom and auto-follow. Timeline height and zoom preferences are browser-local, not project settings.
- **Dependencies and assets:** No FFmpeg binary/library, AI model, cloud provider, database, plugin system, telemetry, or credential store is included. The project-card background is decorative, not a real thumbnail. The supplied icon's redistribution rights have not been independently verified.
- **Verification:** Automated tests cover project migration/validation (including backward-compatible track gain/pan), generic timeline operations, export-size and target-bitrate calculations, waveform peak extraction and mocked in-session waveform rendering, local media-file preflight and metadata failures/timeouts, simulated browser playback/clock behavior, and mocked WebM export success, cancellation, low-cadence warning, automatic-capture fallback, and recorder-error cleanup paths. A real Chromium 153/Linux smoke run with a synthetic 4-second VP8/Opus fixture verified local import, metadata, preview playback, cancellation (restored the export button without a download), and the automatic-capture fallback with `requestFrame` disabled. After correcting export-clock accumulation and starting capture from a decoded frame, repeated default 1080p WebM exports decoded with 20–28 video frames over 4 seconds (120 expected at 30 fps); FFmpeg decoded the audio stream without timestamp warnings. Resolution diagnostics produced 54 encoded packets at 1280×720 (43 Chromium frame callbacks), 72 at 960×540, and 98–109 at 640×360 over 4 seconds (120 expected). Lower output sizes improved sandbox throughput. These diagnostics predate the current selectable resolution and target-bitrate controls; neither they nor the control integration test validate finished output quality or target-device performance. Chromium replayed the 640×360 file to EOF (3.994 s, 87 presented-frame callbacks), while FFmpeg decoded its audio and reported no video warnings. A latest 1080p export replayed to EOF at 4.067 s but produced only 16 presented-frame callbacks from 21 video packets; its last video packet was timestamped 3.602 s, while the audio stream continued to 4.067 s. The low-cadence warning appeared in that run at 6.8 estimated canvas fps. An A/B comparison of redundant full-canvas clears showed no measurable cadence gain. Frame cadence remains unacceptable for finished work and output quality is not verified. These results do not establish whether the remaining bottleneck is specific to this browser/runtime/device or the export implementation; repeat on supported target hardware before relying on export. Tests still do not cover pixel-level output quality, browser memory behavior, mouse/touch behavior in all browsers, or Windows hardware compatibility. No installer test has been run.
