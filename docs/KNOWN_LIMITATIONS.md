# Known limitations — foundation build 0.1.0

ClipWright is a browser-based editing foundation, not a complete desktop video editor.

- **Packaging and storage:** The unsigned x64 NSIS installer was built by GitHub Actions, passed its packaged-renderer/preload smoke test, and the installed build was confirmed working. It is still an unsigned preview, not a supported public release, and there is no portable build. The Windows desktop app provides native `.cwproject` open/save, 650 ms debounced autosave for linked files, atomic replacement, and up to ten recovery checkpoints per project; project-list entries/documents and preferences also remain in browser-profile localStorage. Browser builds continue to use local storage and explicit download snapshots. Source media is never bundled, and browser-picked media must be relinked after restart.
- **Media references:** Local video and audio files are inspected in-browser and held in memory through revocable object URLs for the current page session. Project documents retain filename-only `browser-session` references and metadata, never media bytes or temporary URLs. Relinking is required after reload. Imported path references are not automatically verified or resolved. Import/relink preflight rejects empty files and obvious media-kind/MIME mismatches, probes metadata before replacing a session source, and prevents overlapping reads; decoder/codec compatibility still depends on the browser. Image picker ingestion is not supported.
- **Codec and frame accuracy:** Preview uses native browser `<video>` decoding. Container/codec support, seek latency, and actual presented frames depend on the browser and operating system. Timeline times and edits are quantized to the project frame rate, but preview seeking is still controlled by browser media elements and is not a decoder-level frame-accurate guarantee. Export separately uses timestamped Mediabunny frame readers; the synthetic packaged Windows production path has passed, while real user-media output and target-device behavior remain unverified. Browser-reported duration is not independently verified against container metadata.
- **Playback scope:** The timeline is the master clock and advances with `requestAnimationFrame`; video elements follow it, two decks preload the next active source, source-time drift is corrected, gaps render black, and playback stops at the last clip on any track. Audio clips on separate tracks play and mix against that clock, follow seeks/trims, and honor track mute, per-track gain/pan, saved audio-track solo, plus the shared preview-volume control. Track hide/show and audio solo persist in the project and affect export. Preview is a single active video clip, not a composited multi-layer output. On-demand stereo waveform previews are session-only, not saved in project documents, and limited to relinked files up to 20 MB and 3 minutes. Decoding currently runs in the renderer and may briefly affect responsiveness. Audio automation and audio effects are not included.
- **Editing and export scope:** Clip move, same-type track changes, trim, split, normal/ripple delete, multi-selection, marquee selection, snapping, copy/paste/duplicate at the playhead, and session-only undo/redo are implemented. Track mute/lock, audio gain/pan, and hide/show/solo render state are project-persisted; undo history is not serialized and resets when the page closes. WebM export uses a shared saved-project service and the existing WebCodecs/Mediabunny VP9/Opus pipeline. Before success it requires exact frame counts, monotonic video PTS, three lightweight decoded content probes, required readable audio-track presence, explicit per-track/container duration bounds, and effective encoder configuration; failure saves a local diagnostic without media. At 30 fps/48 kHz/1 ms timebase the enforced limits are 17.167 ms video PTS, 10.521 ms audio onset/A/V, 20.521 ms audio duration, and 20.521 ms container duration when audio is expected. It offers sequence resolution plus 720p/540p/360p long-edge presets and compact/standard/high bitrates. The output is buffered in memory; this is not offline desktop rendering or a full compositor. The packaged saved-project/FFmpeg validation passed on one Windows CI runner; imported user media and long-run memory behavior are not certified. Offline sources produce black/silent segments. No effects, captions, AI analysis, transcription, or reframing are included.
- **Layout:** The editor stays below the project top bar. Navigation and media panels collapse; the preview/timeline divider is resizable. Track headers and ruler remain fixed while the timeline canvas scrolls, with responsive zoom and auto-follow. Timeline height and zoom preferences are browser-local, not project settings.
- **Dependencies and assets:** No FFmpeg binary/library, AI model, cloud provider, database, plugin system, telemetry, or credential store is included. The project-card background is decorative, not a real thumbnail. The supplied icon's redistribution rights have not been independently verified.
- **Verification (current branch):** Local `npm test` passes 86 tests across 12 files; `npm run test:desktop` passes 9 tests; `npm run build` completes TypeScript and all three renderer builds. Windows CI run [40879301564](https://github.com/yetiwrld/ClipWright/actions/runs/40879301564) passed the packaged saved-project production export and independent FFmpeg/ffprobe full video/audio decode and measurement checks. It reported VP9/Opus, 65/65 decoded frames, 109 Opus packets, zero of 65 identity mismatches, video/audio/container durations of 2.166/2.1735/2.180 s for a 2.166667 s expectation, and all measured deviations inside the documented tolerances. CI uploaded the synthetic media and reports; artifact download from this environment returned EOF. This Linux environment has no Xvfb, Chromium GUI, FFmpeg, ffprobe, or `DISPLAY`. Neither fixture validates user media, long encoded output, synchronization for real sources, all codecs/devices, or target hardware. Physical hardware encoding is not established by the reported WebCodecs config. Earlier pre-change sandbox diagnostics remain historical only: 1080p exports produced 20–28 frames over 4 seconds versus 120 expected; subsequent 720p/540p/360p runs produced 54/72/98–109 packets respectively and were inadequate. The former 22.646 s report remains unexplained: 667 frames at 30 fps is 22.233333 s, a 0.412667 s difference; the original file/log/device context is unavailable, and a 22.21 s expectation would still round up to 667 frames. Keep playback callback/drop metrics distinct from encoded-file measurements. Long-duration 30000/1001 encoded output, user-media A/V sync, memory pressure, cancellation/failure recovery on packaged builds, and broad Windows hardware coverage remain open.
